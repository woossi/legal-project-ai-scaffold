# ppt-deck

## 구성

- `contract/deck.schema.json` — `02_deck.json` 의 구조 계약 (JSON Schema)
- `contract/outputs.json` — 선행조건·멱등성·값 도메인·교차 제약
- `references/문체-판정.md` — 제목·종결어미 판정 경계 사례. 애매한 것만 모은다
- **`scripts/` 를 두지 않는다.** 덱 스펙 작성은 판단이고 기계화 대상이 아니다.
  스펙의 **검사**는 `ppt-verify` 의 검증기가 맡는다

## 서술 규칙 (정본)

### 규칙 1 — 제목은 역할명형 명사구다. 문장을 쓰지 않는다

덱 제목과 슬라이드 제목은 **그 덱이 무슨 역할인지 명명**한다. 서술어를 넣지 않는다.

| | 형태 | 예 |
|---|---|---|
| 권장 | `Task N — <대상 명사구>` 또는 `작업 N — <대상 명사구>` | `작업 1 — 시행지침 수집`<br>`작업 2 — 목차구조 전수조사`<br>`작업 3 — 위임축 규범값 추출` |
| 권장 | 역할명 단독 | `수집 범위`·`검증 게이트 구성`·`미해결 항목` |
| 금지 | 완전한 문장 | `자동검증은 오류는 잡았지만, 누락은 놓쳤다` |
| 금지 | 결론형·서술형 | `그런데 분석 결과 문제가 있었다`·`수집을 완료했다` |

판정 기준은 하나다 — **제목에 서술어(용언 종결형)가 있으면 위반이다.**
`~다`·`~했다`·`~이다`·`~한다`로 끝나면 전부 걸린다. 연결어미(`~지만`·`~고`)도 문장의 표지다.
`문제가 있었음`·`검증을 완료함`처럼 완결절을 명사화한 제목도 위반이다. 본문에서 쓰는
`~함`·`~됨`·`~임` 종결을 제목에 옮기지 않는다.

### 규칙 2 — 본문은 명사형 종결로 두텁게 쓴다

본문 항목이 설명 책임을 가진다. 제목은 역할만 명명하고, 결과·근거·한계는 본문에 적는다.

| | 형태 | 예 |
|---|---|---|
| 권장 | `~함`·`~됨`·`~임`·`~음` | `189개 지구 시행지침 수집함`<br>`정의문 추출 165건 성공함`<br>`OCR 유래 43건 포함됨` |
| 권장 | 명사구 종결 | `분모 165 기준`·`전수조사 미완` |
| 금지 | 서술형 종결 | `수집했다`·`성공한다`·`포함되어 있다` |

한 슬라이드 본문은 **3~7개 항목**을 기본으로 한다. 한 항목이 두 줄을 넘으면 쪼갠다.

### 규칙 3 — 모든 수치는 `fact_refs` 로 결박한다

본문에 숫자가 있으면 그 항목에 `fact_refs` 가 있어야 한다. 값은 `01_source.json`
의 `facts[].id` 를 가리킨다. **덱 스펙에서 수치를 직접 계산하거나 원자료를 다시
파싱하지 않는다.** 그 일은 `ppt-curator` 가 이미 끝냈다.

숫자 토큰마다 `claims[]`에 `display_value`와 `fact_ref`를 적는다. `display_value`는
본문 또는 시각 캡션에 실제로 표시한 값이다. 검증기는 표시값과 fact 값을 직접 대조한다.

비율 fact가 `denominator_fact`를 쓰면 그 fact도 함께 참조한다. 비율 fact가
`denominator` 수치를 직접 가지면 해당 비율 fact 하나를 참조해도 된다. 이 프로젝트는
모수가 갈리는 이력이 있다. 189(전체 문서)와 165(정의문 추출 성공)를 섞지 않는다.

### 규칙 4 — 현 프로젝트의 작업 경계를 세 단계로 고정한다

현 프로젝트 발표의 `work_boundaries`는 아래 순서를 사용한다.

1. `작업 1 — 수집 단계(자료 수집 및 정제)` — 원본 PDF·HWP와 변환 Markdown을 입력으로 원문을 확보하고, 조문 경계·정의 조항·규범 문장을 분리하며 문언후보를 생성
2. `작업 2 — 법 적용 확인` — 기준일·사업 시기·시행 기간·조문 근거를 비교해 적용·미적용·확인 필요를 기록
3. `작업 3 — 스키마 설계 및 구현` — Project Core 클래스·관계·통제어휘와 검증 규칙을 설계하고 구현

작업 1에서 `스키마`는 조문 파싱 구조와 산출물 계약을 의미한다. 이 용어를 Project Core
클래스·관계 스키마와 같은 결과로 표시하지 않는다. 정의환경을 사용하지 않은 임베딩 군집은
문언후보로 표시하며 자동 정규화 결과로 표시하지 않는다.

발표자료 제작·검증은 세 작업 체계를 설명하는 보조 운영 내용이다. 이 내용을 별도 작업
번호로 추가하지 않는다.

`role: task`인 슬라이드는 `work_boundary`를 반드시 가진다. 수집 결과를 스키마 구현 결과로
분류하거나, 검증 워크플로우를 수집 결과로 분류하지 않는다. 한 작업이 두 경계에 걸리면 그
작업이 만든 최종 산출물의 소유 경계를 기준으로 한 곳에만 배치한다.

### 규칙 5 — 작업 설명보다 결과와 결론을 불릿으로 제시한다

task 슬라이드의 `body[]`는 2단계 계층을 사용한다. 1단계 불릿은 `level: 1`과 `kind`를
가지며, `kind` 값은 `결과`, `결론`, `남은 한계` 중 하나다. 2단계 불릿은 `level: 2`를
가지고 `kind`를 갖지 않는다. task 슬라이드는 세 `kind`의 1단계 불릿을 각각 하나 이상
포함한다. 각 1단계 불릿 직후에는 하위 근거를 하나 이상 둔다. `범위`는 표지·연결·마무리에서만
사용한다.

- `결과`는 기준 기간에 확인된 수치·산출물·검증 판정을 제시한다.
- `결론`은 결과가 다음 판단이나 설계에 의미하는 바를 제시한다.
- `남은 한계`는 결과에서 닫히지 않은 검증 범위를 제시한다.
- 1단계 결과 불릿은 `190개 지구`처럼 핵심 수치를 요약할 수 있다. 2단계 불릿은 그 수치의
  관측 단위·세부 수치·판정 근거를 확장한다.
- 2단계 불릿은 `관측 단위 — …`, `확정 수치 — …`, `판정 근거 — …`, `후속 대상 — …`처럼
  상위 판단을 확인할 수 있는 대상을 먼저 제시한다.

코드 수정, 파일 작성, 명령 실행 같은 활동 목록은 본문에 넣지 않는다. 재현에 필요한 파일명과
실행 절차는 발표자 노트의 `[Sources]` 블록에 둔다. 렌더러는 1단계를
`• 결과 — …`·`• 결론 — …`·`• 남은 한계 — …`로 표시하고, 2단계를 들여쓴
`◦ …`로 표시한다.

## 기존 정본과의 관계

`docs/ppt/`는 채택된 발표자료를 보관하는 정본 경로다. 새 덱은 그 경로를 자동으로
상속하지 않는다. `docs/ppt/design.md` 는 `20260813.pptx` 를 역분석한 디자인 시스템이다. 그중
**서술 규칙(9.2 · 6절 Do)은 이 스킬이 오버라이드한다.**

| 항목 | `design.md` | 이 스킬 | 근거 |
|---|---|---|---|
| 제목 | 결론형 한 줄. 권장 예 `자동검증은 오류는 잡았지만, 누락은 놓쳤다` | 역할명형 명사구 | 사용자 지시 (2026-08-26) |
| 종결 | 능동형 `수집했다`·`연결했다` | 명사형 `수집함`·`연결함` | 사용자 지시 (2026-08-26) |

**시각 토큰은 오버라이드하지 않는다.** `docs/ppt/design-tokens.json` 의 색·타이포·
간격·캔버스는 충돌이 없으므로 **선택 가능한 프로필**로 그대로 쓸 수 있다.
`02_deck.json` 의 `profile` 이 `docs-ppt-20260813` 이면 그 토큰을 적용하고,
`none` 이면 렌더러 기본값을 쓴다. 디자인 양식 자체는 자율이다.

`design.md` 의 나머지(색 의미 고정, 한 장 한 인과, 전문용어 번역표 9.3)는 유효한
참고다. 특히 **9.3 용어 번역표**는 재사용 대상이다 — `SHACL → 형식·경로 검증`,
`IRI → 식별자`, `PARTIAL → 미검증`.

## 실행

1. **`01_source.json` 을 읽는다.** 없으면 시작하지 않고 `ppt-curator` 에 요청한다.
   이 스킬은 상류 파일을 만들지 않는다.
2. **작업 경계를 먼저 나눈다.** `work_boundaries`를 고정 순서로 선언하고 각 task에
   `work_boundary`를 하나 배정한다.
3. **덱 역할을 나눈다.** 슬라이드를 쓰기 전에 `작업 1..N` 의 이름 목록을 정한다.
   각 작업은 `01_source.json` 의 어떤 fact 묶음을 소비하는지 먼저 대응시킨다.
   대응되는 fact 가 없는 작업은 만들지 않는다.
   기준 덱의 여정 레일을 잇는 슬라이드는 `stage` 를 `1..6`으로 적는다. 단계는
   `수집 → 내용 보존 → 적용 범위 → 근거 연결 → 누락 검증 → 전국 확대` 순서다.
4. **슬라이드별로 `purpose` 를 한 줄 적는다.** 이 슬라이드가 없으면 무엇이 안 보이는지.
   `purpose` 는 명사형 종결 규칙의 예외다 — 스펙 내부 메모이며 렌더되지 않는다.
5. **계층형 불릿을 채운다.** 결과·결론·남은 한계를 1단계에 두고, 각 판단의 관측 단위·수치·
   근거·후속 대상을 2단계에 둔다. 수치 항목에 `fact_refs` 또는 `claims`가 누락되면 그 항목을 지운다.
6. **시각자산을 붙인다.** `visuals[].path` 는 `output/viz/**` 의 기존 산출물을 가리킨다.
   슬라이드당 시각자산은 1개로 제한한다. **새 그림이 필요하면 만들지 않고 `viz` 팀에 요청한다.**
   이 스킬은 그림을 소유하지 않는다.
7. **자기 검사.** 작업 경계 세 갈래, task별 결과·결론·남은 한계, 제목 문체, 수치 전건의
   `fact_refs`와 `claims`를 확인한다. 센 결과를 보고에 적는다.

## 반려 조건

상류를 고치지 않는다. 아래는 스펙 작성을 멈추고 반려한다.

- `01_source.json` 의 `facts[]` 가 비어 있음
- 쓰려는 수치의 `fact` 에 `as_of` 또는 `measured_by` 가 없음
- 비율 fact에 `denominator`와 `denominator_fact`가 모두 없음
- `sources[].sha256` 과 실제 파일 해시가 어긋남 — 상류가 갱신됐다는 뜻이며
  `ppt-curator` 재실행이 필요하다

## output path

`output/ppt/<deck-id>/02_deck.json` 하나만 쓴다.
`01_source.json`·`build/**`·`03_qa.*` 를 건드리지 않는다.
