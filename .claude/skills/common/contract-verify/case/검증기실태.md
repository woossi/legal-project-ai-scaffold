# 검증기 실태

기존 검증기 11개를 전건 읽고 실제로 돌려 확인한 대조표다. 공통 절차를 정하기 전에
무엇이 이미 다른지 여기서 본다. 각 항목은 코드를 읽거나 실행해 확인한 것만 담는다.

이 조사 뒤에 `legal-xref/verify_contract` 와 `legal-coverage/verify_contract` 가
등록돼 현재 등록부는 13건이다. 이 문서의 대조표는 조사 시점의 11건을 담으며,
뒤에 등록된 둘의 검사 대상·종료코드는 `contract/verifier_registry.json` 이 정본이다.
아래 10절의 실측 수치도 조사 시점의 것이다 — 갱신 수치는 리포트에서 읽는다.

측정 시점 2026-08-12 · 인터프리터 Python 3.14.6 · jsonschema 4.23.0 설치, rdflib·pyshacl
미설치(요구사항에는 선언돼 있으나 `.venv_kb/` 에 따로 있다).

# 0. 종료코드와 실행 규약 (SKILL.md 에서 옮겨온 상세)

- `0` = 실패 없음 · `1` = 실패 있음 · `2` = 검증 불가
- 미검사는 **두 자리**에서 나온다 — 선행조건 미충족(실행 안 함)과 종료코드 2(검증 불가)
- **종료코드만으로 갈라서는 안 된다.** 이 저장소의 검증기 넷은 `2=검증 불가` 를 선언하고도
  `sys.exit(문자열)` 이라 실제로는 1 을 낸다(실측, 아래 3절). 그래서 선행조건을 레지스트리에
  선언하고 **실행 전에** 판정한다
- 검증기는 `cwd=저장소 루트` 로 띄운다. 셋은 상대 경로 기본값을 써서 다른 곳에서 돌리면
  데이터 결손과 구분되지 않는 실패를 낸다
- 리포트에는 검증기별 종료코드·소요시간·stdout/stderr 요약·첫 오류줄을 담는다.
  실패를 요약으로 대신하지 않는다

## 사각지대의 실측 근거

- **자기 일관성의 한계** — 도수분포 13칸·유형합·교차표 행열합이 전부 일치하고 산술도
  완벽했으나 판정 규칙에 구멍이 5개 있었고 산술 검증은 그중 하나도 잡지 못했다
- **총합이 상쇄한 손실** — 합계 비교로는 잡히지 않는다. 실측 4건(7행)이 이렇게 묻혔다
- **하한 검증의 반대 방향** — `기록값 < 실측` 만 보는 지표는 부풀림을 구조적으로 놓친다.
  실측 171건이 그림 마커 3,817개만큼 부풀고도 전건 통과했다
- **원자료 대조 범위** — 원문 md 를 보는 것은 `--full` 을 켠 legal-term 계열 3개와
  `legal-xref/verify_contract --full` 뿐이다. 나머지는 산출물 안에서 닫힌다
- **환각 검사와 귀속 검사는 다르다** — `legal-xref/verify_contract --full` 은 표기가 근거
  발췌에 실재하는지만 본다. 그 표기가 **누구 것인가**는 보지 않아, 별표 82건이 외부 문서
  소유인데 내부로 확정된 채 전건 통과했다(2026-08-12 반박검증). 통과 보고에 이 구분을 적는다

# 2. 종료코드 — 선언과 실제가 어긋난다

네 검증기의 docstring 이 `2=검증 불가` 를 선언한다. 그런데 그 자리의 구현은
`sys.exit("[2] 산출물 없음: …")` 로 **문자열**을 넘긴다. 파이썬은 문자열 인자를 stderr 에
찍고 종료코드 **1** 을 낸다. 실측으로 확인했다.

```
python3 -c "import sys; sys.exit('[2] 산출물 없음: /nope')"   # → 종료코드 1
```

- `legal-dup/verify_contract:172` · `legal-term/verify_contract:64,68` ·
  `legal-toc/verify_contract:20,24` · `legal-textreform/verify_contract:59`
- 실제로 2 가 나오는 자리는 `legal-term/verify_contract:158,164`(`--full` 의 git 참조
  부재)와 `legal-dup/verify_contract:184` 뿐이다

**결과: 입력 부재와 계약 위반이 같은 종료코드 1 로 합쳐진다.** 세 갈래로 집계하려면
종료코드만 봐서는 안 되고 선행조건을 실행 전에 따로 봐야 한다. 이 스킬이 선행조건을
레지스트리에 선언하는 이유다.

`verify_definitions` · `verify_doc_definitions` · `verify_statute` 는 애초에 2 를 쓰지
않는다. 산출물이 없으면 `return 1` 이라 데이터 결손과 구분되지 않는다.

# 3. jsonschema 미설치 대응이 네 갈래다

| 검증기 | 없을 때 | 결과 |
|---|---|---|
| `legal-dup/verify_contract` | 내장 검증기로 폴백 | 계속. 지원 키워드 12종으로 좁혀 검사 |
| `legal-term/verify_contract` | `sys.exit("[2] jsonschema 미설치")` | **검증 전체 중단** |
| `verify_definitions` · `verify_doc_definitions` · `verify_statute` | 경고로 남기고 스키마만 건너뜀 | 교차 제약은 계속. 부분 미검사 |
| `legal-contrast/verify_contract` | 해당 없음 | 스키마의 `required` 를 직접 순회한다 |

legal-dup 의 내장 검증기가 지원하는 키워드는 `type` · `enum` · `required` ·
`properties` · `items` · `$ref` · `$defs` · `additionalProperties` · `minLength` ·
`minimum` · `exclusiveMinimum` · `pattern` 이다. 그 밖의 키워드가 계약에 들어오면
조용히 미검사가 된다 — 경고가 없다.

legal-contrast 의 직접 순회는 **배열의 첫 원소만 본다**(`verify_contract.py:69-75`).
`doc[key][0]` 하나에 필수 필드가 있으면 나머지 원소는 보지 않는다.

# 4. JSON Schema draft 가 갈리지만 어긋나지는 않는다

스키마 파일 8개 중 draft-07 4개(statute 2 · legal-term definitions·doc_definitions),
2020-12 4개(contrast · dup 2 · terms)다. 검증기가 쓰는 Validator 도 같은 폭으로 갈려
있어 현재는 맞물린다.

- `Draft7Validator`: `verify_definitions` · `verify_doc_definitions` · `verify_statute`
- `Draft202012Validator`: `legal-dup/verify_contract` · `legal-term/verify_contract`

`contrast.schema.json` 만 2020-12 를 선언하고도 jsonschema 에 한 번도 넘어가지 않는다.

**공통 검사기는 draft 를 고정하면 안 된다.** `check_outputs_contract.py` 는
`jsonschema.validators.validator_for(schema)` 로 스키마 선언에서 검증기를 고른다.

# 5. 보고 형식이 다섯 갈래다

| 형식 | 검증기 | 특징 |
|---|---|---|
| `✗` 줄 + `위반 N건` | legal-dup · legal-term/verify_contract · legal-toc · legal-textreform/verify_contract | 위반만 출력 |
| `fails`·`warns` 누적 + `실패 N건` / `계약 통과` | verify_definitions · verify_doc_definitions · verify_statute | 경고를 실패와 분리한다 |
| `OK`/`FAIL` 전건 나열 | legal-contrast | **통과 항목까지 나열하는 유일한 검증기** |
| `[PASS]`/`[FAIL]` + `--json` | legal-textreform/verify | **기계 판독 출력이 있는 유일한 검증기** |
| `[OK ]`/`[FAIL]`/`[SKIP]` + 게이트 번호 | validate_ontology · verify_chain | 세 갈래 표기 |

실패 표지가 `✗` · `FAIL` · `  - ` · `Traceback` 로 흩어져 있어 한 패턴으로는 잡히지
않는다. `run_verifiers.py` 의 `ERROR_MARKS` 가 이 다섯 갈래를 함께 훑는 이유다.

# 6. 미검사를 아는 검증기는 하나뿐이다

`verify_chain.py` 만 게이트마다 `pass`/`fail`/`skipped` 세 갈래를 내고 마지막에
`실패 N · 미검사 N / 6` 으로 집계한다. 나머지 10개는 두 갈래다.

같은 스킬의 `validate_ontology.py` 조차 두 갈래다 — `_gate()` 가 `ok` 를 bool 로만
받아(`"pass" if ok else "fail"`) skipped 를 표현할 자리가 없다. 게이트 3·4 는 그래프가
비었을 때 `"그래프가 비어 있어 문법 검사만 수행"` 이라는 detail 을 달고 **pass** 로
집계한다. 미검사가 통과로 흡수된 자리다.

# 7. 저장소 루트 산정이 세 갈래다

| 방식 | 검증기 | 실행 위치 의존 |
|---|---|---|
| `os.path.abspath(os.path.join(HERE, "..", ×5))` | legal-dup · legal-term/verify_contract · legal-toc · legal-textreform/verify_contract | 없음 |
| `Path(__file__).resolve().parents[5]` | legal-contrast | 없음 |
| 루트를 구하지 않고 **cwd 상대 기본값** | verify_definitions · verify_doc_definitions · verify_statute | **있음** |

세 번째 갈래는 `--file output/legal/word/definiation.json` 처럼 상대 경로를 기본값으로
둔다. 저장소 루트가 아닌 곳에서 돌리면 `산출물 없음` 으로 종료코드 1 을 내며, 이는 데이터
결손과 구분되지 않는다. `run_verifiers.py` 가 모든 검증기를 `cwd=저장소루트` 로 띄우는
이유다.

kb-ontology 둘은 `os.path.join` 만 쓰고 `abspath` 를 걸지 않아 경로에 `..` 이 남는다.
동작에는 지장이 없으나 출력 경로가 길어진다.

# 8. 진입점과 인자 처리

| 관례 | 검증기 |
|---|---|
| `sys.exit(main())` | verify_definitions · verify_doc_definitions · verify_statute · legal-contrast |
| `raise SystemExit(main())` | validate_ontology · verify_chain |
| `main()` 안에서 `sys.exit()` | legal-dup · legal-term/verify_contract · legal-toc · legal-textreform ×2 |

argparse 를 쓰지 않는 것이 둘이다. `legal-toc/verify_contract` 는 인자를 아예 받지
않고, `legal-contrast/verify_contract` 는 `"--full" in sys.argv` 로 직접 본다 —
`--help` 가 없고 오타를 잡지 못한다.

# 9. 계약 파일의 이름과 형식이 어긋난다

| 스킬 | 계약 파일 | 형식 |
|---|---|---|
| legal-statute · legal-term | `outputs.json` | `outBase` + `files{}` (영문 camelCase 키) |
| legal-contrast | `outputs.json` | **한국어 키** — `산출물[]`·`선행조건`·`값도메인`·`교차제약`·`판정파라미터` |
| legal-dup | `commands.json` | `outBase` + 명령 정의 |
| legal-toc | `columns.json` | `outBase` + `file` + `columns[]` |
| legal-textreform | `frontmatter.json` | `outBase` + `fields`·`fieldOrder`·`originItem` |
| kb-ontology | `ontology.json` 외 2 | 클래스·술어·IRI 패턴 |

**같은 이름의 파일이 다른 형식이다.** `check_outputs_contract.py` 가 legal-contrast 를
미검사로 가르는 것은 결손이 아니라 이 형식 차이다. 형식을 통일하는 것은 이 스킬의
담당이 아니다 — 각 팀 스킬의 계약은 그 팀이 정한다.

# 10. 실측 결과 (2026-08-12, worktree 체크아웃)

```
run_verifiers.py          통과 7 · 실패 0 · 미검사 4 / 등록 11 (총 3.18초)
check_outputs_contract.py 통과 2 · 실패 1 · 미검사 1 / 대상 4
```

조사 시점의 등록 11건 기준이다. `legal-xref`·`legal-coverage` 검증기를 등록한 뒤
같은 체크아웃에서 다시 돌리면 **통과 9 · 실패 0 · 미검사 4 / 등록 13** 이었다.
그 뒤 main 을 병합하며 `legal-statute/verify_guideline_articles` 가 추가돼 현재는
**통과 10 · 실패 0 · 미검사 4 / 등록 14** 다. 미검사 4건과 그 사유는 아래와 같다.

미검사 4건과 사유:

| 검증기 | 사유 |
|---|---|
| `legal-dup/verify_contract` | 입력 없음 `output/legal/시행지침/*/*/` — 원본 8.8GB 가 `.gitignore` 로 미추적 |
| `legal-textreform/verify` | 입력 없음 `output/legal/**/*.txt` — 변환 중간 산출물이 저장소에 0건 |
| `kb-ontology/validate_ontology` | 모듈 없음 `rdflib` · `pyshacl` |
| `kb-ontology/verify_chain` | 모듈 없음 `rdflib` |

**`legal-dup` 을 선행조건 무시하고 강행하면 190건이 `디렉터리 없음` 으로 잡힌다.** 이는
계약 위반이 아니라 입력 부재다. 실패로 집계하면 거짓 경보가 나머지 검사를 덮는다.

`check_outputs_contract.py` 의 대상이 4건인 것은 측정 중 `legal-coverage` 스킬이
새로 만들어졌기 때문이다(계약 `outputs.json` 1파일 검사·통과). 이 스킬은 두 검사기의
발견 방식이 다름을 보여준다 — `check_outputs_contract.py` 는 디스크를 훑어 자동으로
집었고, `run_verifiers.py` 는 레지스트리를 읽으므로 집지 못했다. **등록부는 조용히
낡는다.** `run_verifiers.py` 가 디스크의 `verify*.py`·`validate*.py` 를 훑어 미등록
검증기를 경고로 알리는 이유다(실패로 세지는 않는다 — 새 스킬이 만들어지는 중일 수 있다).

이 경고는 실제로 제 몫을 했다. 측정 직후 `legal-xref`·`legal-coverage` 검증기 2건이
미등록으로 걸려 등록부에 반영됐고, `check_outputs_contract.py` 의 대상도 4건에서
5건(`legal-xref` 추가)으로 늘었다. 등록부가 낡는 속도가 이만큼 빠르다.

`check_outputs_contract.py` 의 실패 1건은 `legal-term/core_terms.json` 이다. 계약이
`schema: terms.schema.json` 을 선언했는데 85개 항목 전건이 `occurrences` 필수 필드를
갖지 않는다. `core_terms.json` 은 `df>=18 경량본` 이라 `occurrences` 대신 `districts` 를
싣는다. legal-term 의 검증기는 스키마를 `terms.json` 에만 걸고 `core_terms.json` 에는
id 부분집합만 보므로(`verify_contract.py:135-144`) 이 어긋남이 지금까지 드러나지 않았다.
